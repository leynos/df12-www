# Architectural decision record (ADR) 0001: Render the site with MiniJinja on free-threaded CPython

## Status

Accepted on 2026-11-19. The site generator now renders through MiniJinja and
requires free-threaded CPython 3.15.2 or newer with the GIL disabled.

## Date

2026-11-19.

## Context and problem statement

The site is generated by `df12_pages`, which renders every page from YAML,
Markdown and MiniJinja templates. The generator previously used Jinja2 3.1.6. A
full `pages generate --all-sites` run spent most of its wall-clock time inside
the template engine: 26.988 s of 33.565 s in a five-run comparison, with the
remainder spread across HTTP replay, Markdown and Mermaid rendering, Pygments
highlighting and file I/O.

The generator also renders one `PageContentGenerator` per documentation bundle,
and those bundles are independent of one another. Jinja2's environment and
render path hold interpreter state that makes concurrent rendering across
threads unattractive under the global interpreter lock (GIL). The build was
therefore serial, even though the work is naturally parallel and the host has
spare cores.

The question is which template engine and runtime should replace that
combination, and how many document bundles should render concurrently by
default.

## Decision drivers

- Page generation dominates the build, so engine throughput matters more than
  any other single component.
- The site must stay reproducible: the same inputs must produce the same bytes,
  and the reference capture date must remain fixed for browser checks.
- The templates are already MiniJinja-compatible in syntax; the migration should
  not require rewriting page copy or component macros.
- The escaping rules already differ by page kind (HTML and XML documents versus
  `.jinja` sub-site pages) and must be preserved exactly.
- The build machine has several cores, and documentation bundles are
  independent, so concurrency is available for free if the runtime permits it.

## Options considered

_Table 1: Template engines and runtimes compared._

| Option                                          | Template throughput                   | Thread concurrency                  | Migration cost                  | Reproducibility                    |
| ----------------------------------------------- | ------------------------------------- | ----------------------------------- | ------------------------------- | ---------------------------------- |
| Jinja2 3.1.6 on GIL CPython                     | Baseline (26.988 s per all-sites run) | Serial under the GIL                | None                            | Unchanged                          |
| MiniJinja 3.1.0 on GIL CPython                  | 0.843 s per all-sites run             | Still serial                        | Small: syntax and filter wiring | Preserved                          |
| MiniJinja 3.1.0 on free-threaded CPython 3.15.2 | 0.843 s per all-sites run             | Eight document bundles concurrently | Small, plus the runtime pin     | Preserved, including worker counts |

The 0.843 s entries are the template-processing step of the Jinja2-to-MiniJinja
comparison, which ran both engines on CPython 3.13.11. It measures the engine
change alone, so the free-threaded row reuses that number rather than claiming
a separately measured 3.15.2t value; the runtime change is measured by the
page-generation sweep in the [benchmark report](../minijinja-benchmark.md),
8.70 s serial against 5.63 s with eight workers on CPython 3.15.2t.

## Decision outcome

Adopt MiniJinja 3.1 with free-threaded CPython 3.15.2, and render documentation
bundles through a thread pool that defaults to eight workers.

- `.python-version` pins `cpython@3.15.2t`, which is what makes uv install and
  select the free-threaded build in a checkout. `requires-python` states the
  minimum version, `>=3.15.2`, so an installer refuses an older interpreter,
  but it neither names CPython nor says anything about the GIL. The CLI guards
  the other two conditions and re-checks the version, refusing to run when the
  interpreter is older than 3.15.2, is not CPython, or reports the GIL enabled.
  The guard matters because a free-threaded interpreter can still be started
  with the GIL on, through `PYTHON_GIL=1` or `-X gil=1`.
- `df12_pages/templating.py` owns the shared environment, the per-suffix
  escaping policy, the reproducible `SOURCE_DATE_EPOCH` timestamp and the
  `highlight` filter, so every builder renders through one configuration.
- `PageContentGenerator` splits fetching, preparation, rendering and writing.
  `prepare_document()` is the remaining command: it registers the template
  directory and compiles Mermaid figures. `render_document()` is then a query
  over the prepared values and the provenance it is handed, including the build
  timestamp, so it reads no file, environment variable or subprocess;
  `RenderedDocument.write()` publishes the result. `_publish_documents` owns
  the pool and the ordered publication: it renders a worker-sized batch
  concurrently but writes each bundle in configuration order, so a later bundle
  still wins a shared path. `_write_documents` builds the render closure, logs
  the timing and delegates to it.
- `--doc-workers` and `INPUT_DOC_WORKERS` override the default of eight; one
  worker gives the serial behaviour for comparison.

On one interpreter, CPython 3.15.2t with the GIL disabled, eight workers cut
all-sites page generation from 8.70 s to 5.63 s, 25.8% against the committed
serial generator. The interpreter change did not pay for itself on its own: the
same sweep took 7.58 s on CPython 3.13.11 and 8.70 s on 3.15.2t. The complete
warm build fell from 22.56 s to 20.50 s, and the engine change alone cut
all-sites page generation from 33.56 s to 7.23 s.

## Known risks and limitations

- Free-threaded CPython is newer than the GIL build, and a dependency without a
  free-threaded wheel can still import or run under the GIL. The CLI check
  proves the runtime, not that every extension module is GIL-free.
- MiniJinja is not Jinja2. Its import cache and finalizer semantics differ, so a
  test that relied on Jinja2's module caching had to render a whole call
  sequence in one template instead.
- The default worker count is tuned for the build host and the observed
  documents. A slower or busier host should measure its own optimum; the count
  is configurable for that reason.
- The benchmark report records the measurement method and its profiler
  limitations; the figures are not a claim about every host.

## Architectural rationale

The decision keeps rendering as a build-time, static-output concern. Work done
once at generation time is cheaper than work done in the browser on every
visit, and the site ships no client-side framework. Making the runtime
free-threaded lets the existing independent-bundle structure use the host's
cores without introducing an async framework, shared mutable render state or a
new output pipeline. Publishing in configuration order keeps the output
independent of scheduling, which is what makes the concurrency safe to adopt.
